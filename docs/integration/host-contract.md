## Registration and lifecycle

The ES module entry exports `register(on, options)`; `options` comes from manifest `userConfig` with defaults applied. Files may use JS or TS extensions. `hooks/hooks.json` points to the entry using `{"modules":["./register.js"]}`. The plugin also needs `.claude-plugin/plugin.json`.

Declaration shapes:

```ts
Register = (on: On, options: PluginOptions) => unknown
PluginOptions = Readonly<Record<string, string | number | boolean | readonly string[]>>
on(pattern, hook)
on(pattern, matcher, hook)
hook($, e, next)
```

`on` yields a registration supporting `.catch(handler)`. Ordinary handlers are async functions; current reference names `turn.step` and `process.spawn` as async-generator hooks. Event input is deeply frozen; alterations must be copied into `next`. `next(e)` invokes later hooks and host behavior and resolves their result. `next.signal` is an AbortSignal for abandoned event work. A handler can answer without calling next.

`session.start` runs before the first prompt and on mod reload. It does not rerun after `/clear`, `/resume`, `/branch`. `session.end` does fire on those operations and on shutdown; all end handlers share a default 1.5-second budget. Do not wait indefinitely during cleanup. Timers are automatically cancelled when the module reloads.

## Commands

Register in `session.start` and handle a literal matcher:

```js
on('session.start', async ($, e, next) => {
  await $.command.register({ name: 'pulsedeck', description: 'Open PulseDeck', immediate: true })
  return next(e)
})
on('command.run', { command: 'pulsedeck' }, async ($, e) => {
  // e.args is everything typed after the command name, or ''.
  return {}
})
```

`CommandSpec` has required `name: string`, `description: string`, optional `argumentHint: string`, `immediate?: true`. Registration resolves `{ command: string }`. Names are letters, digits, underscore or hyphen, maximum 64. A built-in collision throws; register commands last or catch registration failure. `immediate: true` permits execution while Claude is working.

Handler output `{}` prints nothing; `{ text: string }` prints command output and Claude reads it. The older declarations also permit optional `context: string[]` and `ref` in CommandRunResult. Public types expose `$.command.run({ command: string, args?: string }): Promise<CommandRunResult>` through EventCalls. It queues until idle and rejects unknown commands or unsafe invocation from a handler the turn is waiting on. User-facing controls should call mod actions directly when appropriate.

## Processes: verified and unknown

Current API guide explicitly says `$.process.spawn` streams a long-running process and that earlier mods can withhold its output/result. A `process.spawn` hook is an async generator. If another mod withholds a result before reading output to completion, the engine stops a still-running child; if it already read to completion, effects are not undone.

**Not published in the retrieved sources:** exact spawn arguments/options, return handle, stdout/stderr chunk schema, result promise, kill signature, abort option, child reload cleanup, process-group behavior. Public 2.1.277 types contain only `run`. Do not substitute Node ChildProcess conventions (`stdout.on`, `.kill`, PID handling) and present them as host contracts.

Verified one-shot signature:

```ts
$.process.run(argv: readonly string[], init?: {
  cwd?: string; env?: Record<string,string>; stdin?: string; timeoutMs?: number
}): Promise<{exitCode:number; stdout:string; stderr:string}>
```

It uses an argv vector without a shell; relative cwd is relative to the session. Nonzero exit codes resolve. Failure to start or timeout rejects. Default timeout 30 seconds, maximum ten minutes. It waits for collected output, so it is unsuitable for continuous cava output. A signalled child's run exitCode is 1 in the public types.

## Timers

Public type signatures, also corroborated by current API guide:

```ts
$.clock.now(): Promise<number>
$.clock.every(ms: number, fn: () => void): {cancel: () => void}
$.clock.after(ms: number, fn: () => void): {cancel: () => void}
$.clock.sleep(ms: number, options?: {signal?: AbortSignal}): Promise<void>
```

`every` first fires after the interval; minimum interval 1 ms. The guide demonstrates async callbacks. A callback failure is logged and later periods continue. A host policy refusing a timer period ends that timer. The source declarations describe each period as its own dispatch. No `setInterval`/`setTimeout` globals are available in a hook module.

## Files and preferences

Verified filesystem calls:

```ts
$.fs.write(path: string, text: string): Promise<void>
$.fs.read(path: string): Promise<string>
$.fs.read(path: string, {as:'bytes'}): Promise<{base64:string}>
$.fs.exists(path: string): Promise<boolean>
$.fs.list(path?: string): Promise<FsEntry[]>
```

Write creates parent directories and replaces whole content; relative paths resolve from the session cwd. Read/write limit is 4 MiB per file. Neither the current guides nor retrieved public declarations expose `fs.temp`, `fs.tmp`, `fs.remove`, `fs.unlink`, or another named temporary-file/delete API. **Temporary path allocation and removal contracts are unknown.** Any command-based fallback must be deliberate, bounded, and documented as an OS command through process.run, not a native host filesystem method.

Persistent plugin-private JSON store:

```ts
$.store.get(key: string): Promise<unknown>
$.store.set(key: string, value: unknown): Promise<void>
$.store.delete(key: string): Promise<void>
$.store.keys(): Promise<string[]>
```

Unset keys yield undefined. Validate loaded preference objects. Serialization follows JSON; cycles/functions reject, Maps/Sets lose their special form. Total store limit 4 MiB. Use it for preferences, not a live audio buffer.

## AbovePrompt and compositional rendering

Use `on('ui.render', {component:'AbovePrompt'}, ...)`. Read current event fields from `e.props`: `hasSurvey`, `isWorking`, `maxRows`, `bodyColumns`, `scroll`, `view`. `e.requestId` is the host-provided instance string; retain that exact string for blits rather than inventing an AbovePrompt requestId. `e.surface` identifies terminal or desktop. `e.viewport` may be absent; its dimensions describe the whole window. Size the band with bodyColumns and maxRows.

The band is shared. Preserve later mods by including `await next(e)` once in children. Illustrative composition:

```js
on('ui.render', {component:'AbovePrompt'}, async ($, e, next) => {
  if (e.props.hasSurvey) return next(e)
  const {Box, Text} = $.ui.resolve(e)
  const rest = await next(e)
  return Box({flexDirection:'column', children:[
    Text({children:['PulseDeck']}), rest
  ]})
})
```

Element constructors come from `$.ui.resolve(e)` and take props with children; Box/Text are not globals. Unsupported props/elements cause the entire tree to be refused and host fallback to draw. `$.ui.invalidate('ui.render')` returns void. Current reference limits normal invalidations to 10/sec, with 30/sec in terminal for a visible pane, expanded band, and hint; early calls coalesce.

Official sample evidence:

https://github.com/anthropics/claude-code-playground/blob/main/claude-code/mods/token-weather/hooks/token-weather.mjs

This Apache-2.0 sample confirms literal on/API call spelling and top-level helpers accepting $. **It uses flattened `e.hasSurvey`/`e.bodyColumns`, conflicting with current docs and public types' nested e.props. Prefer nested current documented fields.** It also replaces the band without composing next; that is inappropriate if preserving other mods is required.

## Raster and blit

Raster exists only on terminal. Branch on `e.surface` before accessing it; offer Text on desktop.

```ts
Raster({key: string, columns: number, rows: number, cells: string})
$.ui.blit({requestId:string, key:string, cells:string,
  columns?:number, rows?:number}): Promise<{deny?:string}>
```

Dimensions: columns 1..512, rows 1..256. Cells are row-major standard padded base64 encoding exactly columns*rows little-endian u32 triples: [codePoint, foreground, background]. Colors are 0x00RRGGBB; 0x01000000 means terminal default. Glyphs must be printable width-one BMP codepoints. Blocks and braille are valid; avoid emoji/full-width glyphs. Public types describe a palette of 1024 simultaneous foreground/background pairs.

Explicit little-endian packing avoids implicit platform-endian assumptions:

```js
const bytes = new Uint8Array(columns * rows * 12)
const view = new DataView(bytes.buffer)
// For cell index i:
view.setUint32(i * 12, glyph, true)
view.setUint32(i * 12 + 4, foreground, true)
view.setUint32(i * 12 + 8, background, true)
const cells = bytes.toBase64()
```

The current guide demonstrates Uint8Array.toBase64, so Buffer/btoa are unnecessary. Blit addresses the same mounted key and requestId owned by this plugin. Supplied dimensions must match the mounted Raster. Resize with invalidate and a new render; never use blit to resize. Blit repaints without rerunning ui.render. Check returned deny to recover from unmounted/invalid frames. Old types describe coalescing blits to display frames (120 accepted/sec, about 60 shown); the current reference does not promise those throughput numbers, so treat them as stale guidance rather than a supported guaranteed frame rate.

## Panes

```ts
$.ui.open({id:string, title?:string, focus?:true,
  closeOnEscape?:true, holdToasts?:true, rows?:number, columns?:number})
$.ui.close({id:string}): Promise<void>
$.ui.panes(): Promise<readonly UiPane[]>
```

Current guide says open resolves `{isPlaced:true}` or `{isPlaced:false, reason:string}`; public 2.1.277 d.ts says Promise<void>. Follow current guide but validate generated target-build types before relying on the result. Opening again uses the same id, not a second instance. Draw in a Pane hook that checks `e.requestId === id`; pass other panes through next.

Pane props include title, isFocused, bodyColumns, placement, scroll, view. `placement` is dock or inline. Docked height comes from e.props.scroll.bodyRows; inline height is a limit on growing content. Trees beyond body height scroll. rows/columns request positive integer dimensions; user resize wins. Boolean flags accept only true or omission (false is invalid).

Command/press-opened panes show at any width. Autonomous opening needs 144 columns, falling to 110 after a user previously opened the pane. focus is granted only when prompt is empty and other UI does not hold keys. Hotkeys are one digit or lowercase letter. Controls use onPress, onInput/onSubmit, onSelect, and stable keys. Prompt keyboard input remains host-managed.

## Implementation gate

Known enough to build commands, preferences, render composition, Raster packing, resizing, and timer management. **Not enough to honestly implement native streaming capture cleanup through an exact host spawn/kill contract.** Before claiming live capture works, regenerate target-version types and verify spawn streaming, cancellation, and temporary-file handling against that build. Lack of native claude/cava here prevents integration testing; mocks alone cannot establish those host contracts.

Rechecked the complete current reference methods/event tables: process lists only run and spawn; spawn is named as an async-generator event, but no chunk/handle schema appears. fs lists read/write/list/exists/stat/ancestors only, and expressly says write is non-atomic. No native temp/remove or process.kill method is listed.

Concrete capability boundary proposal (an application interface, **not a Claude API assertion**):

```ts
interface CapturePort {
  available: boolean
  reason?: string
  createConfig(text: string): Promise<{path: string; remove(): Promise<void>}>
  spawn(argv: readonly string[], handlers: {
    stdout(chunk: string): void
    stderr(chunk: string): void
    exited(code: number): void
  }): Promise<{stop(): Promise<void>}>
}
```

Default native binding should return available=false with a clear reason until target `/plugin-types` confirms streaming, kill/abort, and config lifecycle. CAVA parser/source orchestration can be tested through an injected port. Never probe for capability by starting capture; no file or child should be created when available=false. Validate enabled port promises idempotent stop, bounded cleanup, no callbacks after stop, rejection on launch error, and per-instance config isolation. Demo source may remain available as an explicitly identified demonstration. This preserves a concrete extension point without inventing a host contract.

## CAVA capture semantics and raw output

Official upstream sources inspected:

- https://github.com/karlstav/cava/blob/master/example_files/config
- https://github.com/karlstav/cava/blob/master/README.md
- https://github.com/karlstav/cava/blob/master/input/pipewire.c
- https://github.com/karlstav/cava/blob/master/input/pulse.c

Current example config says backend selection depends on compiled support; Linux can prefer oss/pipewire/sndio/jack/pulse/coreaudio/alsa/portaudio/fifo. **Always set method explicitly** rather than inherit backend selection.

| Backend | Current documented/source behavior | Output-only setting |
|---|---|---|
| pulse | Example config says auto selects default sink monitor. pulse.c resolves default_sink_name and appends .monitor. README retains a warning that default may be microphone. | Explicit verified output-monitor name ending in .monitor. |
| pipewire | Config says auto uses default sink monitor. pipewire.c sets stream.capture.sink=true for auto. For a name ending .monitor it strips the suffix, sets sink capture, and targets the remaining object name. auto_input omits sink capture and uses default input. | Explicit output-node object name plus .monitor. |
| coreaudio | Config/README describe auto as output device, auto_input as input. System-mix tap requires macOS 14.2+ and compiled tap support. | method=coreaudio, source=tap (stereo) or tap_mono. |
| alsa / portaudio | Capture-device selection can point at input hardware; no automatic output-monitor guarantee. | Require a deliberately chosen loopback device; no fallback to default microphone. |

For PipeWire an arbitrary serial alone can address an input or output. A named .monitor source is a more explicit output-only choice. For Pulse prefer actual source inventory rather than accepting a suffix blindly as proof of a working device. If unavailable, report a capture error; never retry an input backend automatically. Current code supports safe auto semantics for pulse/pipewire, but the README's conflicting warning plus unknown installed CAVA version makes explicit monitor selection the conservative default.

macOS tap failure must remain a failure until the user chooses a known loopback device. No automatic fallback from tap to coreaudio auto_input, portaudio auto, or another microphone input.

Illustrative fixed-width ASCII raw output settings (same fields documented upstream):

```ini
[general]
bars = 32
framerate = 30
[input]
method = pipewire
source = chosen-output-node.monitor
[output]
method = raw
raw_target = /dev/stdout
data_format = ascii
ascii_max_range = 1000
bar_delimiter = 59
frame_delimiter = 10
channels = mono
mono_option = average
```

The 59 delimiter is semicolon and 10 is newline. Raw ASCII values run from zero to ascii_max_range. stdout read chunks need not align with frames; preserve a bounded partial-line buffer. Fixed bar count avoids raw output's documented default of 1024 stereo bars/512 mono bars. Binary format is optional 8bit (0..255) or 16bit (0..65530); prefer ASCII until verified host streaming supports bytes. Config says Linux creates a FIFO for a missing raw_target; target /dev/stdout avoids a custom output FIFO. These are CAVA configuration facts, not verification that host capture is currently wired.

The user now requires one plugin installation to include CAVA, with no separate CAVA installation. This supersedes the earlier system-executable-only setup recommendation. No system-package installation on this research machine was requested or performed.

### Can normal plugin installation execute a CAVA installer?

**No general install/postinstall hook is documented.** The exhaustive manifest fields contain no native-system dependency or installer field; the hook event reference contains no PluginInstall event. `dependencies` means other Claude plugins, not apt/brew packages. An unrecognized top-level manifest field is stripped.

Automatic npm/Bun dependency installation explicitly disables lifecycle scripts. A plugin `package.json` postinstall that downloads/builds/installs CAVA will not run. npm-source plugin fetching also never runs the package's own install scripts. It requires supported package+lockfile formats and package managers on PATH; it is unsuitable as an invisible native installer.

`Setup` is not an installation event: it fires only via explicit --init-only or noninteractive --init/--maintenance launches. `SessionStart` shell hooks can bootstrap dependencies into CLAUDE_PLUGIN_DATA, and the docs demonstrate that pattern, but that is first runtime activation rather than the completed `claude plugin install` operation. It can run again, must be idempotent, and can fail due to networking/toolchain availability. Shell install without a running session loads hooks only on the next startup/reload.

**Exception:** a marketplace's `source: {source:'command', command:'...', timeout:60, mode:'copy'}` deliberately executes a reviewed shell command during installation/update, and again once per session. It must be an executable command on PATH or an absolute path, run from the user's home through sh/cmd.exe, and output exactly one absolute plugin directory path. It must produce a complete plugin directory. Users review/accept the command; shell automation can pass --yes. Administrators may disable command sources. This is an executable source provider, not a normal plugin lifecycle installer; it commonly presupposes a tool already installed and therefore does not inherently solve zero additional setup. A self-contained bootstrap command could assemble the plugin and CAVA, but adds network/platform assumptions and install-time executable trust, and dependencies with command sources are never automatically installed.

### Recommended delivery design

Ship a complete plugin archive/git package containing platform binaries and their required non-OS libraries under `runtime/<os>-<arch>/`. Plugin installation copies those assets into the plugin cache alongside the mod. Use the exact plugin-root path rather than searching PATH or installing system packages. Keep changing state/configuration in CLAUDE_PLUGIN_DATA (created on reference, survives updates). The release package, not postinstall, supplies CAVA.

Feasible initial support promise: macOS arm64/x86_64 at a declared minimum OS with tap support, and a declared Linux x86_64 distribution/libc/audio-server family. Expand after CI verifies each target. The plugin can include more than one platform payload in one install; select the matching payload at runtime and fail clearly on unsupported platforms. Do not promise arbitrary Linux distributions/architectures, old macOS, Windows, SSH/cloud audio, or machines without an output server. Zero separate CAVA installation is achievable; zero OS audio permission prompts or zero pre-existing audio infrastructure is not established by these sources.

Packaging CAVA does not solve the unresolved mods `process.spawn` contract. A version-verified native binding still needs target-generated types and capture cleanup verification. Alternative engineering design, explicitly an application protocol rather than a Claude API: package a native supervisor/bridge with CAVA; a short known `$.process.run` startup operation starts that supervisor and emits a loopback endpoint, then `$.http.fetch` polls bounded JSON frames and sends shutdown. The native supervisor owns CAVA streaming, temporary files, signal handling, and expiry/orphan cleanup. This can use already documented host methods, but requires an implemented/tested bridge and authenticated loopback protocol before being claimed functional. It introduces more product code than a verified spawn binding.

One install can legitimately provide CAVA only once the published package actually contains runnable supported-platform CAVA artifacts plus required libraries/notices. An empty runtime directory, downloader stub, package-manager instruction, or capability-disabled skeleton does not satisfy that requirement. Capture is never attempted through `process.run`, and the native module graph never imports Node. `/plugin-types` and installed-build validation remain required before a native streaming binding can be supplied. The Node-only developer port owns mkdtemp directories, mode-0600 configuration, argv streaming children, bounded callback chunks, and awaited SIGTERM/SIGKILL cleanup. It requires an explicit executable and backend capability declaration; it does not search PATH. Linux `pulse`/`pipewire` require an explicit `.monitor` source for developer overrides; `coreaudio` accepts `tap`/`tap_mono`. `auto_input` is always rejected. Bundled `auto` needs both port and read-only capability attestations of output-only semantics.

### Retryable config-allocation failure extension

The application port contract now permits a rejected `createConfig` error to carry `error.cleanup: {remove(): Promise<void>}` when configuration writing and its immediate removal both fail. This handle owns only cleanup, not a launchable path. CAVA source adopts that ownership, blocks a successor, and exposes explicit `dispose()` retry; cleanup rejection keeps the handle. The Node port also retains the same owner internally, exposes `pendingCleanupCount()` / `retryCleanup()`, and refuses new temp allocation while pending cleanup exists. A successful explicit cleanup removes the pending owner; a fresh source instance may then start. No unknown native cleanup API is invoked. Successful config removal and source teardown share in-flight promises and release ownership only after success.

Source stderr and Node version/error diagnostics now sanitize ANSI sequences, C0/C1/DEL controls and bidi controls, cap retained strings by UTF-8 byte count, and budget application wrappers so emitted diagnostics are at most 2048 bytes. Host renders and Button callbacks carry a lifecycle epoch: a downstream render completing after session disposal returns downstream content unchanged; retired actions do not mutate replacement controllers or save preferences.

### Version-probe ownership (final scoped fix)

Node `check()` registers a probe cleanup owner **before** invoking argv spawn. `pendingCleanupCount()` now counts owned version probes (including launches still pending and cleanup awaiting confirmation) plus failed configuration-directory owners; it excludes successfully returned configuration handles and capture children, whose source/handle owns cleanup. Any such pending owner blocks another check, config allocation, or public Node spawn. The internal version-probe launch alone bypasses that spawn barrier.

Probe cleanup shares an in-flight promise and removes its owner only after spawn resolves/rejects and any adopted child termination succeeds. Failed termination retains the same owner for explicit `retryCleanup()` or `error.cleanup.remove()`; the existing CAVA-source error-cleanup adoption is unchanged. A two-second check timeout returns with a cleanup handle while unresolved spawn remains owned. That same cleanup promise automatically adopts/stops a late handle; a late stop rejection remains pending for explicit retry. No successor probe or capture allocation can bypass the barrier. A successful normal read-only check clears the owner before returning capability data.
